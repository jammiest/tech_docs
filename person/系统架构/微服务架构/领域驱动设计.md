# 领域驱动设计 (Domain-Driven Design)

## 什么是领域驱动设计？

领域驱动设计（DDD）是一种软件开发方法，它通过将项目的核心关注点集中在领域和领域逻辑上，来应对复杂软件系统的开发挑战。

## 核心概念

### 1. 统一语言 (Ubiquitous Language)

**开发团队和领域专家使用统一的术语进行沟通。**

```markdown
示例：
- 业务术语: "订单"、"库存"、"客户"
- 避免技术术语: 不要使用"DTO"、"Entity"等技术词汇与业务人员交流
- 代码反映业务: 类名、方法名应该使用业务语言
```

### 2. 限界上下文 (Bounded Context)

**明确界定某个模型的应用边界。**

```javascript
// 不同的限界上下文有不同的模型
// 订单上下文
class Order {
  constructor(orderId, items, totalAmount) {}
}

// 物流上下文  
class Shipment {
  constructor(trackingNumber, deliveryAddress, status) {}
}

// 虽然都叫"订单"，但在不同上下文中含义不同
```

### 3. 上下文映射 (Context Mapping)

**描述不同限界上下文之间的关系。**

| 映射模式 | 描述 | 示例 |
|---------|------|------|
| **合作关系** | 两个团队协同工作 | 订单服务与库存服务 |
| **客户-供应商** | 上游为下游提供服务 | 用户服务为订单服务提供用户数据 |
| **遵奉者** | 下游遵从上游的模型 | 报表服务使用订单服务的模型 |
| **防腐层** | 隔离外部系统的影响 | 集成第三方支付系统 |
| **共享内核** | 共享部分模型和代码 | 公共的基础设施组件 |

## 战略设计模式

### 子域划分 (Subdomain Types)

#### 核心域 (Core Domain)
```markdown
- 业务的竞争优势所在
- 投入最多的开发资源
- 示例: 电商的推荐算法、 Uber的调度系统
```

#### 支撑子域 (Supporting Subdomain)
```markdown
- 支持核心业务但不是差异化因素
- 示例: 用户管理、权限系统
```

#### 通用子域 (Generic Subdomain)
```markdown
- 行业通用解决方案
- 可以考虑购买或使用开源方案
- 示例: 支付处理、邮件发送
```

## 战术设计模式

### 实体 (Entity)
**具有唯一标识和生命周期的对象。**

```java
public class User {
    private Long userId;  // 唯一标识
    private String name;
    private String email;
    
    // 行为方法
    public void changeEmail(String newEmail) {
        this.email = newEmail;
    }
}
```

### 值对象 (Value Object)
**没有唯一标识，通过属性值定义的对象。**

```java
public class Address {
    private String street;
    private String city;
    private String zipCode;
    
    // 值对象通常是不可变的
    public Address(String street, String city, String zipCode) {
        this.street = street;
        this.city = city;
        this.zipCode = zipCode;
    }
    
    @Override
    public boolean equals(Object o) {
        // 基于属性值比较
    }
}
```

### 聚合 (Aggregate)
**一组相关对象的集合，有一个根实体作为入口点。**

```java
public class Order {  // 聚合根
    private Long orderId;
    private List<OrderItem> items;
    private Customer customer;
    
    // 保护不变规则
    public void addItem(Product product, int quantity) {
        // 业务规则验证
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        items.add(new OrderItem(product, quantity));
    }
}
```

### 领域服务 (Domain Service)
**处理不适合放在实体或值对象中的业务逻辑。**

```java
public interface OrderCalculationService {
    BigDecimal calculateTotal(Order order);
    BigDecimal applyDiscounts(Order order, Customer customer);
}
```

### 领域事件 (Domain Event)
**表示领域中发生的重要事件。**

```java
public class OrderCreatedEvent {
    private Long orderId;
    private LocalDateTime createdAt;
    private Customer customer;
    
    public OrderCreatedEvent(Order order) {
        this.orderId = order.getId();
        this.createdAt = order.getCreatedAt();
        this.customer = order.getCustomer();
    }
}
```

### 仓库 (Repository)
**提供聚合的持久化抽象。**

```java
public interface OrderRepository {
    Order findById(Long orderId);
    void save(Order order);
    void delete(Order order);
}
```

### 工厂 (Factory)
**负责复杂对象的创建逻辑。**

```java
public class OrderFactory {
    public Order createOrder(Customer customer, List<OrderItem> items) {
        Order order = new Order(customer);
        items.forEach(order::addItem);
        
        // 复杂的初始化逻辑
        if (customer.isVIP()) {
            order.applyVIPDiscount();
        }
        
        return order;
    }
}
```

## DDD与微服务结合

### 服务边界划分
```markdown
1. 每个限界上下文 → 一个微服务
2. 聚合根 → 服务的API边界
3. 领域事件 → 服务间通信机制
```

### 示例：电商系统划分
```bash
# 基于DDD的微服务划分
user-context/          # 用户限界上下文
  └── user-service

order-context/         # 订单限界上下文  
  └── order-service

inventory-context/     # 库存限界上下文
  └── inventory-service

payment-context/       # 支付限界上下文
  └── payment-service
```

## 实施步骤

### 1. 事件风暴 (Event Storming)
```markdown
- 召集领域专家和开发团队
- 识别领域事件、命令、聚合
- 建立统一语言
- 划分限界上下文
```

### 2. 领域建模
```markdown
1. 识别实体和值对象
2. 定义聚合和聚合根
3. 设计领域服务
4. 确定仓库接口
```

### 3. 实现模式
```java
// 分层架构示例
@ApplicationService
public class OrderApplicationService {
    
    @DomainService
    private OrderCalculationService calculationService;
    
    @Repository
    private OrderRepository orderRepository;
    
    public Order createOrder(CreateOrderCommand command) {
        // 应用服务协调领域对象
        Order order = orderFactory.create(command);
        calculationService.calculateTotal(order);
        orderRepository.save(order);
        
        // 发布领域事件
        eventPublisher.publish(new OrderCreatedEvent(order));
        return order;
    }
}
```

## 最佳实践

### ✅ 正确做法
```markdown
- 持续与领域专家沟通
- 使用业务语言命名
- 保持聚合的小而专注
- 通过领域事件实现最终一致性
```

### ❌ 避免做法
```markdown
- 贫血模型（只有getter/setter）
- 技术逻辑污染领域层
- 过大的聚合设计
- 忽略限界上下文边界
```

## 总结

> 重要：DDD不是银弹，它最适合复杂业务领域。对于简单CRUD应用，传统的分层架构可能更合适。

**DDD的核心价值：**
- 建立业务与技术的桥梁
- 创建可维护的复杂系统
- 支持业务的持续演进
- 为微服务架构提供设计指导
